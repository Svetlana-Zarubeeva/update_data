# Управление миграциями базы данных (Custom Orchestrator)

В проекте используется кастомный оркестратор миграций (`db.py`), который управляет `Alembic`.
**Важно:** Стандартные команды `alembic upgrade` / `alembic downgrade` использовать **нельзя**, так как цепочки зависимостей отключены (`down_revision=None`). Порядок применения определяется строго датой в имени файла.

История примененных миграций хранится в таблице `public.migration`.

### Создание новой миграции
Создает новый файл миграции, автоматически добавляя текущий timestamp в имя файла для корректной сортировки.
Команда:
`python3 db.py create "описание миграции"`

Пример:
`python3 db.py create "add_users_table"`
*Результат: будет создан файл вида `2025_12_01_120000_add_users_table.py`.*

### Применение миграций (Upgrade)
Накатывает все новые миграции, которых еще нет в базе. Скрипт сортирует файлы по дате и применяет их по очереди.
Команда:
`python3 db.py upgrade`

### Откат миграций (Downgrade)
Откатывает **только одну** последнюю примененную миграцию (по дате/имени файла). Удаляет запись из истории.
Команда:
`python3 db.py downgrade`

### Решение проблем (Рассинхрон)
Если вы вручную удалили таблицы или база данных была очищена, но скрипт считает, что миграции уже применены (или наоборот), выполните очистку истории в БД:

```sql
TRUNCATE TABLE public.migration;
DELETE FROM alembic_version;
```
После этого запустите `python3 db.py upgrade` для повторного наката.
